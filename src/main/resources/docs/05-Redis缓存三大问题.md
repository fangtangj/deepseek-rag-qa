# 第 4 讲 Redis 缓存三大问题

## 一、为什么要用缓存

数据库连接数是有限的，磁盘 IO 是慢的。当热点数据被高频访问时，每次都查数据库会让数据库成为瓶颈。缓存把热点数据放在内存里，把读请求挡在数据库之外。

引入缓存的收益：

- **降低数据库压力**：大部分读请求被缓存拦截。
- **提升响应速度**：内存读比磁盘读快几个数量级。

引入缓存的代价：**数据一致性变复杂**，以及下面要讲的三大经典问题。

## 二、缓存穿透

### 2.1 现象

查询一个**数据库中不存在**的数据。缓存里没有，数据库里也没有，于是每次请求都会穿过缓存直接打到数据库。

### 2.2 为什么会发生

- **恶意攻击**：用大量不存在的 id 高频请求，故意绕过缓存打数据库。
- **业务代码问题**：查询条件本身就不合法（如 id = -1）。

### 2.3 危害

缓存形同虚设，请求全部落到数据库，可能把数据库打挂。

### 2.4 解决方案

| 方案 | 做法 | 优缺点 |
|---|---|---|
| **缓存空值** | 数据库查不到时，也把一个空对象（或特殊标记）写入缓存，设置较短的过期时间（如 60 秒） | 实现简单；缺点是会占用缓存空间，且短时间内的数据不一致（新建后要等过期） |
| **布隆过滤器** | 在缓存前加一层布隆过滤器，把所有存在的 key 预先放进去。请求先过过滤器，不在的直接拒绝 | 空间效率高、拦截率高；缺点是有**误判**（判断存在可能不存在），且**不支持删除**元素 |
| **参数校验** | 在入口层校验参数合法性，如 id 必须为正整数、必须符合格式 | 治标，能挡掉一部分低级攻击 |

**生产常用组合**：参数校验 + 缓存空值，量级大时再加布隆过滤器。

### 2.5 布隆过滤器原理简述

布隆过滤器是一个位数组加多个哈希函数。插入元素时，用多个哈希函数算出多个位置置 1。查询时，如果有一个位置是 0，说明**一定不存在**；如果全是 1，说明**可能存在**（因为可能是其他元素置的位）。所以它只有"假阳性"，没有"假阴性"。

## 三、缓存击穿

### 3.1 现象

某个**热点 key** 突然过期（或从没被缓存过），此时大量并发请求同时发现缓存失效，一起涌向数据库去查同一个数据。

### 3.2 与穿透的区别

- 穿透：查的是**不存在**的数据。
- 击穿：查的是**存在**的数据，只是缓存恰好失效。

### 3.3 危害

某一个热点数据，瞬间把数据库的并发压力拉满。

### 3.4 解决方案

| 方案 | 做法 | 优缺点 |
|---|---|---|
| **互斥锁** | 只允许一个线程去查数据库并重建缓存，其他线程等待 | 保证一致性；缺点是其他线程要等待，吞吐下降 |
| **逻辑过期** | 缓存里不设物理过期时间，而是存一个逻辑过期时间字段。发现逻辑过期时，异步开一个线程去重建，当前请求先返回旧数据 | 不阻塞请求、吞吐高；缺点是有短暂的数据不一致（返回旧值） |
| **热点数据永不过期** | 热点 key 不设过期，通过后台任务主动更新 | 简单；缺点是数据更新不及时 |

**选择建议**：要求强一致用互斥锁；追求高可用、能接受短暂旧数据用逻辑过期。

## 四、缓存雪崩

### 4.1 现象

**大量 key 在同一时间集体过期**，或者 **Redis 服务本身宕机**，导致所有请求同时打到数据库。

### 4.2 与击穿的区别

击穿是"一个热点 key 失效"，雪崩是"**大批 key 同时失效**"或"**整个缓存服务不可用**"。

### 4.3 解决方案

| 方案 | 做法 |
|---|---|
| **过期时间加随机值** | 在基础过期时间上加一个随机偏移（如 30 分钟 ± 5 分钟），打散过期时间点 |
| **多级缓存** | 本地缓存（Caffeine）+ Redis，Redis 挂了还有本地缓存兜底 |
| **缓存预热** | 系统上线前，先把热点数据加载进缓存，避免启动瞬间全部请求打数据库 |
| **熔断降级** | 用 Sentinel / Hystrix 对数据库访问做熔断限流，保护数据库不被彻底打垮 |
| **Redis 高可用** | 用哨兵（Sentinel）或集群（Cluster）保证 Redis 本身不单点 |

## 五、三者对比速查

| 维度 | 缓存穿透 | 缓存击穿 | 缓存雪崩 |
|---|---|---|---|
| 数据是否存在 | 数据库里**不存在** | 数据库里**存在** | 存在，但大面积失效 |
| 触发范围 | 单个或多个无效 key | **单个热点 key** | **大批 key** 或整个缓存 |
| 核心危害 | 无效请求打到数据库 | 同一热点数据并发打到数据库 | 数据库瞬间被打垮 |
| 首选方案 | 缓存空值 + 布隆过滤器 | 互斥锁 / 逻辑过期 | 过期时间加随机 + 多级缓存 |
| 记忆口诀 | **查不到** | **一个热点过期** | **一片一起过期 / Redis 挂了** |

## 六、缓存与数据库的一致性

缓存和数据库是两份数据，更新时必然存在窗口期的不一致。常见的更新策略：

### 6.1 四种组合对比

| 策略 | 问题 |
|---|---|
| 先更新数据库，再更新缓存 | 并发下可能缓存被旧值覆盖 |
| 先更新缓存，再更新数据库 | 同样有覆盖问题 |
| 先删缓存，再更新数据库 | 删除后、更新前有请求读到旧值并回填缓存 |
| **先更新数据库，再删缓存** | **最推荐**。不一致窗口最小 |

### 6.2 为什么推荐"先更新库，再删缓存"

- 删缓存比更新缓存好：更新缓存要做复杂计算且可能被后续操作覆盖，删除更简单安全。
- 先更新库再删缓存：即使删缓存失败，也只是留下旧缓存，等它过期，不会造成新的不一致。
- 删除缓存失败可以用**消息队列重试**或**订阅数据库 binlog（Canal）**来补偿。

### 6.3 延迟双删

极端并发下，即使"先更新库再删缓存"也可能被脏读回填。**延迟双删**的做法是：

1. 先删一次缓存。
2. 更新数据库。
3. 延迟一段时间（如 500ms，大于一次读请求的耗时）后再删一次缓存。

第二次删除用来清掉并发窗口期里被回填的旧值。

## 七、本讲小结与面试高频问题

**必须能回答的问题**：

1. 缓存穿透、击穿、雪崩分别是什么？三者怎么区分？

**核心记忆**：

- 穿透 = **数据库里没有**（查不到）
- 击穿 = **一个热点 key 过期**
- 雪崩 = **一大批 key 同时过期 / Redis 挂了**
