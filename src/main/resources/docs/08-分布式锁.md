# 第 5 讲 分布式锁

## 一、为什么需要分布式锁

### 1.1 从本地锁说起

单体应用里，多个线程竞争同一资源，用 `synchronized` 或 `ReentrantLock` 就够了。因为所有线程在同一个 JVM 里，锁对象是共享的。

### 1.2 本地锁为什么失效

当应用部署成多个实例（多台机器或多个容器），每个实例都有自己的 JVM。此时：

- 实例 A 的 JVM 锁，实例 B 根本看不见。
- 两个实例同时拿到各自的锁，同时执行临界区代码，互斥失效。

典型场景：**选课系统防超卖**。课程剩余 10 个名额，两个实例各自用自己的本地锁，结果卖出 20 份。

### 1.3 分布式锁的定义

分布式锁是**跨进程、跨机器**的互斥机制。某个进程拿到锁后，其他进程必须等待锁释放才能进入临界区。

## 二、分布式锁必须满足的条件

一个合格的分布式锁，至少要满足：

1. **互斥性**：任意时刻，只有一个客户端能持有锁。
2. **不死锁**：持有锁的客户端崩溃后，锁必须能自动释放，不能让后续请求永久阻塞。
3. **解铃还须系铃人**：只能由加锁的客户端释放锁，不能误删别人的锁。
4. **可重入性（可选但常用）**：同一个客户端重复加锁时，应该能再次获得锁而不是自己阻塞自己。
5. **高可用**：锁服务本身不能单点，否则锁服务挂了整个业务瘫痪。

## 三、基于 Redis 的分布式锁（重点）

### 3.1 第一版：SETNX

```
SETNX lock_key 1
```

`SETNX`（SET if Not eXists）只在 key 不存在时设置成功，天然具备互斥性。

**问题**：如果客户端加锁成功后崩溃，没来得及删除 key，这把锁就永远存在，其他客户端全部阻塞，形成死锁。

### 3.2 第二版：加过期时间

```
SET lock_key 1 NX EX 10
```

设置锁的同时指定 10 秒过期时间，即使客户端崩溃，锁也会自动释放。

**注意**：必须用**一条命令**同时设置值和过期时间，不能用先 `SETNX` 再 `EXPIRE` 两步——两步之间如果崩溃，还是死锁。Redis 2.6.12 之后 `SET` 支持 `NX` 和 `EX` 选项，正好解决这个问题。

**问题**：如果业务执行时间超过了 10 秒，锁提前过期，其他客户端拿到锁，此时两个客户端都在临界区，互斥被破坏。

### 3.3 第三版：value 存唯一标识

```
SET lock_key <uuid> NX EX 10
```

value 存一个客户端唯一标识（如 UUID + 线程 ID）。

**问题**：如果客户端 A 的锁已过期，客户端 B 拿到了锁，此时 A 执行完业务去删锁，会把 B 的锁误删。

### 3.4 第四版：用 Lua 脚本释放锁

释放锁时，必须先判断"这把锁是不是我的"，判断和删除必须是**原子的**：

```lua
-- KEYS[1] = 锁的 key
-- ARGV[1] = 客户端唯一标识
if redis.call('get', KEYS[1]) == ARGV[1] then
    return redis.call('del', KEYS[1])
else
    return 0
end
```

**为什么要用 Lua**：Redis 执行 Lua 脚本时是原子的，中间不会插入其他命令。如果用"先 GET 判断再 DEL"两步，判断和删除之间锁可能被别的客户端抢走或过期被删，导致误删。

### 3.5 第五版：看门狗自动续期（Redisson）

上面的方案还有最后一个问题：**锁的过期时间不好定**。定短了业务没跑完锁就过期；定长了客户端崩溃后其他请求要等很久。

**Redisson** 的解法是**看门狗（Watch Dog）**机制：

- 加锁时如果不指定过期时间，默认用 30 秒。
- 加锁成功后，Redisson 启动一个后台定时任务，每 10 秒（过期时间的 1/3）检查一次，如果业务还没执行完，就把过期时间重置为 30 秒，即"续期"。
- 客户端崩溃后，定时任务停止，锁在 30 秒后自然过期。

**面试要点**：看门狗只在使用 `lock()` 不传超时时间时生效；如果调用 `lock(10, TimeUnit.SECONDS)` 显式指定了超时，看门狗不会启动。

### 3.6 Redisson 完整用法

```java
RLock lock = redissonClient.getLock("lock:course:select:" + courseId);
try {
    // 尝试加锁，最多等 3 秒，锁自动释放时间不指定（用看门狗续期）
    boolean acquired = lock.tryLock(3, TimeUnit.SECONDS);
    if (!acquired) {
        throw new BusinessException("系统繁忙，请稍后重试");
    }
    // 临界区：扣减库存
    doSelectCourse(courseId, studentId);
} catch (InterruptedException e) {
    Thread.currentThread().interrupt();
} finally {
    // 释放锁前判断是否还是当前线程持有
    if (lock.isHeldByCurrentThread()) {
        lock.unlock();
    }
}
```

## 四、RedLock 及其争议

### 4.1 为什么需要 RedLock

如果 Redis 是主从架构（Master-Slave），主节点在加锁成功后、同步到从节点前宕机，从节点晋升为新主，锁就丢了。RedLock 就是为解决这个问题提出的。

### 4.2 RedLock 的做法

客户端向 **N 个（通常 5 个）独立的 Redis 节点**依次加锁。如果：

- 在**超过半数**的节点上加锁成功，**且**总耗时小于锁的有效时间，

则认为加锁成功。否则在已成功的节点上释放锁并重试。

### 4.3 争议

分布式系统专家 Martin Kleppmann 撰文质疑 RedLock：

- 它依赖系统时钟，时钟漂移可能导致锁失效。
- 它无法保证强一致，性能上却没比单节点好多少。
- 如果有 GC 停顿或网络延迟，客户端可能在"已失去锁"的情况下继续操作。

RedLock 作者 antirez 进行了反驳，但社区普遍认为：**RedLock 不是强一致保证，不能用于对正确性要求极高的场景**。日常业务用单节点或主从 + Redisson 已足够。

## 五、基于 ZooKeeper 的分布式锁

### 5.1 原理

ZooKeeper 的节点分为持久节点和临时节点。利用"临时顺序节点"实现锁：

1. 每个客户端在锁目录下创建一个**临时顺序节点**，如 `/lock/lock-0000001`。
2. 获取锁目录下所有子节点并排序，判断自己是不是最小的那个。
3. 是最小的，则获取到锁。
4. 不是最小的，则**监听自己前一个节点的删除事件**（不是监听最小节点，避免羊群效应）。
5. 前一个节点删除时收到通知，再次判断自己是否最小，是则获取锁。

### 5.2 优势

- **自动释放**：客户端断开连接后，临时节点自动删除，锁自动释放。
- **强一致**：ZooKeeper 基于 ZAB 协议，保证数据的强一致性。
- **天然避免羊群效应**：采用链式监听而非全量监听。

### 5.3 劣势

- **性能低于 Redis**：每次加锁解锁都要创建、删除节点，以及节点间的通知。
- **依赖 ZooKeeper 集群**：运维成本高于单机 Redis。

## 六、基于数据库的分布式锁

### 6.1 唯一索引法

建一张锁表，对锁标识建唯一索引。加锁时插入一条记录，插入成功即加锁成功，插入失败（唯一键冲突）即加锁失败；释放锁时删除记录。

优点：实现简单，不引入额外中间件。缺点：数据库操作性能差，且删除失败同样有死锁风险。

### 6.2 悲观锁（select ... for update）

```
SELECT * FROM lock_table WHERE lock_key = 'xxx' FOR UPDATE;
```

利用数据库行锁实现互斥。

缺点：行锁在事务提交前一直持有，容易长时间占用连接和锁资源；且必须谨慎处理事务边界，容易造成死锁。

**结论**：数据库锁只适合并发量极低、又不想引入 Redis/ZK 的兜底场景，一般不用。

## 七、三种实现方式对比

| 维度 | Redis（Redisson） | ZooKeeper | 数据库 |
|---|---|---|---|
| 实现难度 | 低（Redisson 封装好） | 中 | 低 |
| 性能 | 高 | 中 | 低 |
| 一致性 | 最终一致（主从切换可能丢锁） | 强一致 | 强一致 |
| 自动释放 | 靠过期时间 + 看门狗 | 临时节点自动删除 | 靠超时清理 |
| 死锁风险 | 低 | 低 | 中 |
| 适用场景 | **高并发、大多数业务** | 对强一致要求高 | 极低并发兜底 |

**面试结论**：绝大多数互联网业务用 **Redis + Redisson**；金融等强一致要求高的场景用 ZooKeeper。
