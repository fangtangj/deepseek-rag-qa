# 第 3 讲 MySQL 索引原理与 SQL 优化

## 一、索引是什么

索引是帮助 MySQL **高效获取数据的数据结构**。没有索引时，查询只能全表扫描，逐行比对；有了索引，可以直接定位到目标数据所在的页，避免读入无关数据。

一个直观类比：索引就是书的目录。要在一本 500 页的书中找"线程池"这个词，没有目录只能一页一页翻，有目录就能直接跳到对应页码。

## 二、为什么 InnoDB 用 B+ 树

这是索引章节面试出现频率最高的问题。要答清楚，必须先说清楚其他结构为什么不行。

### 2.1 逐个排除

| 数据结构 | 为什么不用 |
|---|---|
| **哈希表** | 等值查询 O(1) 很快，但**不支持范围查询和排序**。`where age > 18` 只能全表扫。 |
| **有序数组** | 等值和范围查询都快，但**插入删除要移动大量元素**，O(n)，不适合频繁写入。 |
| **二叉搜索树** | 极端情况退化成链表，查询变 O(n)（比如按顺序插入 id）。 |
| **平衡二叉树（AVL）** | 不会退化，但**每个节点只存一个元素、最多两个子节点**，树高很高。磁盘 IO 次数 = 树高，几百万数据树高约 20 层，要读 20 次磁盘。 |
| **B 树** | 树高降低了，但**每个节点既存索引又存数据**，导致单页能放的索引项变少，树高仍然偏高；而且 B 树的非叶子节点也存数据，范围查询需要中序遍历，效率不如 B+ 树。 |

### 2.2 B+ 树的优势

B+ 树是 B 树的改良版，关键差异：

1. **只有叶子节点存数据，非叶子节点只存索引键**。因此单个磁盘页能容纳更多的键，树更矮。一个页 16KB，一个键假设 8 字节，一页能放上千个键，三层 B+ 树就能索引上千万行数据。
2. **所有叶子节点用双向链表相连**。范围查询（如 `between A and B`）只要定位到起点，然后沿链表顺序读即可，不需要回到根节点。
3. **树高稳定**。所有数据都在同一层的叶子节点，每次查询的 IO 次数一致，即树高（通常 2–4 层）。

**一句话总结**：B+ 树用"非叶子节点不存数据"换来了更矮的树和更少的磁盘 IO，用"叶子链表"换来了高效的范围查询。

## 三、聚簇索引与二级索引

### 3.1 聚簇索引（主键索引）

InnoDB 是**索引组织表**：表数据本身就存储在聚簇索引的叶子节点上。

- 如果表有主键，主键就是聚簇索引。
- 如果没有主键，InnoDB 选第一个非空唯一索引。
- 如果都没有，InnoDB 会隐式创建一个 6 字节的 rowid 作为聚簇索引。

**叶子节点存的是完整行数据**，所以按主键查询效率最高。

### 3.2 二级索引（辅助索引）

二级索引的叶子节点存的**不是完整行，而是索引列的值 + 主键值**。

因此，通过二级索引查数据分两步：

1. 在二级索引中找到目标记录，拿到主键值。
2. 拿主键值回聚簇索引中查完整行。

第 2 步就叫 **回表**。

### 3.3 回表与覆盖索引

**回表**：`select * from user where name = '张三'`，如果 name 上有二级索引，会先查 name 索引拿到主键 id，再回主键索引查整行，共两次索引查找。

**覆盖索引**：如果查询的所有列都能从索引中直接得到，就不需要回表。例如：

```sql
-- name 和 age 上有联合索引 idx_name_age
select name, age from user where name = '张三';
```

这条 SQL 所需的 name、age 都在索引里，直接从二级索引返回，无需回表。**覆盖索引是重要的优化手段**，EXPLAIN 的 Extra 列会显示 `Using index`。

## 四、最左前缀原则

联合索引 `idx(a, b, c)` 的排序规则是"先按 a 排，a 相同再按 b 排，b 相同再按 c 排"。因此它只能被以下方式用上：

| 查询条件 | 能否用上索引 |
|---|---|
| `where a = 1` | 能（用到 a） |
| `where a = 1 and b = 2` | 能（用到 a、b） |
| `where a = 1 and b = 2 and c = 3` | 能（全部用上） |
| `where b = 2` | **不能**（跳过了最左列 a） |
| `where a = 1 and c = 3` | 部分能用（用到 a，c 用不上排序，只能过滤） |
| `where a like 'x%'` | 能（前缀匹配） |

**重点**：范围查询会"截断"后续列。`where a = 1 and b > 2 and c = 3` 中，a、b 能用索引，但 c 只能作为过滤条件，用不到索引的排序特性。

## 五、索引失效的常见场景

这是排查慢 SQL 的核心清单：

| 场景 | 例子 | 原因 |
|---|---|---|
| 在索引列上做运算或函数 | `where date(create_time) = '2026-01-01'` | 索引存的是原始值，函数运算后无法比较 |
| 类型隐式转换 | `where phone = 13800000000`（phone 是 varchar） | 字符串与数字比较时发生隐式转换，等价于对列做函数 |
| 前导模糊查询 | `where name like '%张'` | 无法确定前缀，只能全扫 |
| 使用 `or` 且两侧不全有索引 | `where a=1 or b=2` | 有一侧没索引，整体退化为全扫 |
| 组合索引不满足最左前缀 | 见上一节 | 无法定位起始位置 |
| 使用 `!=`、`not in`、`is not null` | `where a != 1` | 选择性差，优化器可能放弃索引 |
| 优化器认为全表扫更划算 | 表数据量很小，或索引区分度极低 | 基于成本的决策，不是"失效" |

**注意**：最后一条容易被误判为"失效"。实际上优化器是基于成本估算选择的，索引区分度低（如性别只有男女）时，走索引反而更慢。

## 六、索引下推（ICP）

MySQL 5.6 引入的优化。在联合索引 `idx(a, b)` 下执行：

```sql
select * from t where a = 1 and b like '%x%';
```

没有 ICP 时：先在索引里找到 `a = 1` 的记录，全部回表，再在服务器层过滤 `b`。

有 ICP 时：把 `b like '%x%'` 这个条件下推到存储引擎层，在索引里就先把不满足的过滤掉，**减少回表次数**。

EXPLAIN 的 Extra 会显示 `Using index condition`。

## 七、EXPLAIN 关键字段解读

`EXPLAIN` 是分析 SQL 的第一工具，重点看这几列：

| 列 | 关注点 |
|---|---|
| `type` | 访问类型，性能从好到差：`system > const > eq_ref > ref > range > index > ALL`。出现 `ALL` 表示全表扫描，需要优化 |
| `key` | 实际使用的索引名。为 NULL 表示没用索引 |
| `key_len` | 索引使用的字节数，可推断联合索引用了几列 |
| `rows` | 预估扫描行数，越小越好 |
| `filtered` | 过滤后剩余行的百分比 |
| `Extra` | 附加信息。`Using index` 是覆盖索引（好），`Using where` 表示服务器层过滤，`Using filesort` 表示额外排序（需优化），`Using temporary` 表示用了临时表（需优化） |

**优化目标**：把 `type` 提升到 `ref` 或 `range` 以上，消灭 `Using filesort` 和 `Using temporary`。

## 八、索引设计的实操原则

1. **区分度高的列优先建索引**：如手机号、订单号，而不是性别、状态。
2. **联合索引把等值查询的列放前面，范围查询的列放后面**。
3. **尽量利用覆盖索引**，减少回表。
4. **索引不是越多越好**：每个索引都会占用空间，且降低写入速度（插入要维护所有索引）。
5. **区分度极低的列不单独建索引**。
6. **主键建议用自增整型**：避免页分裂，且占用空间小。
