# 第 1 讲 Java 线程池

## 一、为什么需要线程池

### 1.1 线程的代价

线程不是免费的资源。每创建一个线程，操作系统需要为其分配约 1MB 的栈空间（可通过 `-Xss` 调整），同时线程的创建和销毁都涉及内核态与用户态的切换，开销远大于创建一个普通对象。

### 1.2 不用线程池会有什么问题

如果为每个任务都 `new Thread().start()`，会带来三个问题：

1. **资源耗尽**：请求量上来后线程数无上限增长，最终把内存和 CPU 耗尽。
2. **开销大**：频繁创建销毁线程，CPU 大量时间花在线程调度上而不是业务逻辑上。
3. **无法统一管理**：没有地方统计在线程数、排队任务数，出问题无法定位。

### 1.3 线程池解决什么

线程池的核心思想是**池化复用**：预先创建一批线程，任务来了直接交给空闲线程执行，执行完线程不销毁而是回到池里等下一个任务。收益是：

- 降低资源消耗（线程复用，不用反复创建销毁）。
- 提高响应速度（任务到达时线程已存在，无需等待创建）。
- 提高可管理性（线程数可控，可统计、可监控、可优雅关闭）。

## 二、ThreadPoolExecutor 的七大核心参数

Java 线程池的最终实现是 `java.util.concurrent.ThreadPoolExecutor`，它的构造方法有七个参数，这七个参数必须能背下来并解释清楚：

| 参数 | 类型 | 含义 |
|---|---|---|
| `corePoolSize` | int | 核心线程数。即使线程空闲，也默认保留这么多线程（除非开了 allowCoreThreadTimeOut） |
| `maximumPoolSize` | int | 最大线程数。线程池允许创建的最大线程数量 |
| `keepAliveTime` | long | 空闲线程存活时间。超过核心线程数的那部分线程，空闲超过这个时间就被回收 |
| `unit` | TimeUnit | keepAliveTime 的时间单位，如秒、毫秒 |
| `workQueue` | BlockingQueue | 工作队列。核心线程都在忙时，新任务先放进这个队列 |
| `threadFactory` | ThreadFactory | 线程工厂。用来给线程起名、设置优先级、标记是否为守护线程 |
| `handler` | RejectedExecutionHandler | 拒绝策略。队列满且线程数达到最大值时，如何处理新任务 |

**一个记忆口诀**：核心最大存活时，单位队列工厂拒。（core / max / keepAlive / unit / queue / factory / handler）

## 三、任务提交后的执行流程

这是面试必问的核心问题。当一个任务通过 `execute()` 提交到线程池，判断顺序是：

1. **当前线程数 < corePoolSize**：直接创建新的核心线程执行该任务。
2. **当前线程数 >= corePoolSize**：任务放入工作队列排队。
3. **队列已满，且线程数 < maximumPoolSize**：创建新的非核心线程执行该任务。
4. **队列已满，且线程数达到 maximumPoolSize**：执行拒绝策略。

**关键理解点**：线程池不是"先开满核心线程，再开非核心线程，最后才排队"，而是"核心线程 → 队列 → 非核心线程 → 拒绝"。**队列优先于非核心线程**，这一点很多人会答错。

### 为什么是这个顺序

设计意图是：创建线程比排队更贵。只有当队列都堆满了，说明积压已经严重，才值得付出创建新线程的代价去救急。

## 四、四种拒绝策略

当线程池无法再接受新任务时，由拒绝策略决定怎么办。JDK 内置四种：

| 策略 | 行为 | 适用场景 |
|---|---|---|
| `AbortPolicy` | 直接抛出 `RejectedExecutionException` | **默认策略**。需要感知失败、由调用方决定重试或降级 |
| `CallerRunsPolicy` | 把任务交回给提交任务的线程执行 | 不希望丢任务，且能承受调用方被阻塞（一种天然的反向背压） |
| `DiscardPolicy` | 静默丢弃任务，不抛异常 | 任务可丢、且不想被异常打扰（生产上慎用，会无声丢数据） |
| `DiscardOldestPolicy` | 丢弃队列中最老的任务，再尝试提交当前任务 | 只关心最新任务的场景，如实时状态刷新 |

生产环境常用的做法是自定义拒绝策略：记录日志 + 落库/落盘，避免任务静默消失。

## 五、常见工作队列

| 队列 | 特点 | 风险 |
|---|---|---|
| `ArrayBlockingQueue` | 有界，数组实现，创建时指定容量 | 容量设置需权衡，无界化风险低 |
| `LinkedBlockingQueue` | **默认容量为 Integer.MAX_VALUE**，近似无界 | 线程数永远达不到 maximum，队列无限堆积直到 OOM |
| `SynchronousQueue` | 不存储元素，任务直接交给线程 | 配合 maximumPoolSize 用，适合短任务、高吞吐 |
| `PriorityBlockingQueue` | 带优先级，无界 | 无界，有 OOM 风险 |
| `DelayQueue` | 延迟队列，元素到期才可取出 | 用于定时/延迟任务 |

## 六、Executors 工厂方法的坑（必须记住）

`Executors` 提供了几个快捷创建线程池的方法，但**阿里巴巴 Java 开发手册明确禁止使用**，原因是它们隐藏了队列和线程数的边界：

| 方法 | 问题 |
|---|---|
| `Executors.newFixedThreadPool(n)` | 用的是无界 `LinkedBlockingQueue`，任务堆积会 OOM |
| `Executors.newSingleThreadExecutor()` | 同上，无界队列 |
| `Executors.newCachedThreadPool()` | maximumPoolSize 是 `Integer.MAX_VALUE`，线程数无上限，会 OOM |
| `Executors.newScheduledThreadPool(n)` | 同样是无界队列 |

**结论**：生产环境一律用 `new ThreadPoolExecutor(...)` 显式指定七个参数，队列必须是有界的，拒绝策略必须明确。

## 七、线程池大小怎么定

没有一个万能公式，但有两个基准方向：

- **CPU 密集型**（计算为主，如加解密、复杂计算）：线程数约为 **CPU 核数 + 1**。多出的 1 个用于在某个线程偶发缺页中断时顶上。
- **IO 密集型**（等待网络、磁盘、数据库为主）：线程数约为 **CPU 核数 × (1 + 平均等待时间 / 平均计算时间)**。因为线程大部分时间在等，可以多开一些。

实践中的做法：按上述公式算出初值，再用压测找出最优值，并用监控观察队列积压情况动态调整。

## 八、线程池的状态与关闭

`ThreadPoolExecutor` 内部用一个 `AtomicInteger` 的高 3 位表示状态、低 29 位表示线程数，共五种状态：

| 状态 | 含义 |
|---|---|
| `RUNNING` | 正常运行，接受新任务，处理队列任务 |
| `SHUTDOWN` | 调用 `shutdown()` 后。不接受新任务，但会处理完队列中已存在的任务 |
| `STOP` | 调用 `shutdownNow()` 后。不接受新任务，不处理队列任务，并尝试中断正在执行的任务 |
| `TIDYING` | 所有任务已终止，线程数为 0 时的过渡状态 |
| `TERMINATED` | `terminated()` 方法执行完毕的终态 |

**优雅关闭的正确姿势**：先 `shutdown()` 拒绝新任务，再 `awaitTermination()` 等待已有任务执行完，超时后再 `shutdownNow()` 强制中断。

## 九、常用监控指标

线程池提供了几个方法用于监控：

- `getPoolSize()`：当前线程数。
- `getActiveCount()`：正在执行任务的线程数。
- `getQueue().size()`：队列中排队任务数。
- `getCompletedTaskCount()`：已完成任务总数。

生产上应把这些指标接入监控系统，当队列积压持续增长时告警——这通常是下游变慢或线程数配置不合理的信号。
