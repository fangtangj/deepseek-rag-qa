# 知识点总结

本文件把 8 讲的核心知识点做浓缩汇总，用于复习和考前快速回顾。每个知识点只保留"必须记住"的结论。

## 一、Java 线程池（第 1 讲）

### 必须记住的结论

- **七大参数**：corePoolSize、maximumPoolSize、keepAliveTime、unit、workQueue、threadFactory、handler。
- **执行流程**：核心线程 → 工作队列 → 非核心线程 → 拒绝策略。**队列优先于非核心线程**。
- **四种拒绝策略**：AbortPolicy（默认，抛异常）、CallerRunsPolicy（调用方执行）、DiscardPolicy（静默丢弃）、DiscardOldestPolicy（丢最老的）。
- **禁用 Executors**：`newFixedThreadPool`、`newSingleThreadExecutor` 用无界队列会 OOM；`newCachedThreadPool` 最大线程数无上限会 OOM。
- **线程数经验值**：CPU 密集型 ≈ 核数 + 1；IO 密集型 ≈ 核数 ×（1 + 等待时间 / 计算时间）。
- **五种状态**：RUNNING、SHUTDOWN、STOP、TIDYING、TERMINATED。
- **优雅关闭**：shutdown() → awaitTermination() → 超时再 shutdownNow()。

### 易错点

- 错答"核心满了就开非核心线程"——正确的是**先排队**。
- 误以为 `keepAliveTime` 对所有线程有效——默认只对超过核心数的线程有效。

## 二、Spring Boot 自动装配（第 2 讲）

### 必须记住的结论

- `@SpringBootApplication` = `@SpringBootConfiguration` + `@EnableAutoConfiguration` + `@ComponentScan`。
- 加载入口：`AutoConfigurationImportSelector`。
  - 2.7 前：`META-INF/spring.factories`。
  - 2.7 后：`META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports`。
- **候选类不等于生效类**，是否生效由 `@Conditional` 系列决定。
- `@ConditionalOnMissingBean` 是"用户配置优先"的实现基础。
- 排除自动配置：`@SpringBootApplication(exclude=...)` 或 `spring.autoconfigure.exclude`。
- 自定义 Starter：写自动配置类 + 登记到 imports 文件 + 用 `@ConfigurationProperties` 暴露配置。

### 易错点

- 以为自动配置类只要被列出就一定生效——忽略了条件注解。
- 记混 2.7 前后的文件路径。

## 三、MySQL 索引（第 3 讲）

### 必须记住的结论

- InnoDB 用 B+ 树，原因：非叶子节点不存数据 → 树矮 → IO 少；叶子节点链表 → 范围查询快。
- 哈希不支持范围查询；平衡二叉树树高太高；B 树非叶子也存数据、树高偏高。
- 聚簇索引叶子存整行；二级索引叶子存索引列 + 主键值。
- **回表**：走二级索引后要再查聚簇索引。**覆盖索引**可避免回表（EXPLAIN 显示 `Using index`）。
- **最左前缀**：联合索引 `(a,b,c)` 必须从 a 开始连续匹配；范围查询会截断后续列。
- **索引失效**：列上做函数/运算、隐式类型转换、前导模糊 `%x`、`or` 两侧不全有索引、不满足最左前缀。
- **索引下推（ICP）**：把过滤条件下推到存储引擎，减少回表（EXPLAIN 显示 `Using index condition`）。
- **EXPLAIN 重点列**：type（ALL 最差）、key、rows、Extra（`Using filesort`、`Using temporary` 需优化）。

### 易错点

- 认为索引一定被用上——优化器会基于成本选择，区分度低时可能不用。
- 混淆"回表"与"覆盖索引"的方向。

## 四、Redis 缓存三大问题（第 4 讲）

### 必须记住的结论

| 问题 | 本质 | 首选方案 |
|---|---|---|
| 穿透 | 查数据库**不存在**的数据 | 缓存空值 + 布隆过滤器 |
| 击穿 | **单个热点 key 过期** | 互斥锁 / 逻辑过期 |
| 雪崩 | **大批 key 同时过期 / Redis 挂了** | 过期时间加随机 + 多级缓存 + 熔断 |

- 布隆过滤器：**只有假阳性，没有假阴性**（说不在一定不在，说在可能不在）；不支持删除。
- 缓存一致性首选：**先更新数据库，再删缓存**。
- 延迟双删：删缓存 → 更新库 → 延迟再删一次，清掉并发窗口回填的旧值。

## 五、分布式锁（第 5 讲）

### 必须记住的结论

- 分布式锁要满足：互斥、不死锁、可重入（可选）、释放时校验持有者。
- Redis 分布式锁演进：`SETNX` → `SET key value NX EX`（原子加过期）→ value 存唯一标识 → **Lua 脚本释放**（保证判断与删除的原子性）。
- 生产用 **Redisson**：内置看门狗自动续期、可重入、支持 RedLock。
- ZooKeeper 用临时顺序节点实现锁，靠会话失效自动释放。
- 数据库锁靠唯一索引或 `select ... for update`，性能差，仅作兜底。

## 六、跨讲次关联（面试常被串起来问）

1. **线程池 + 分布式锁**：线程池解决单机内并发资源管理，分布式锁解决跨进程互斥。同一个"资源竞争"问题在两个层次上的解法。
2. **索引 + 缓存**：都是"用空间换时间"的思路。索引把磁盘 IO 降为对数级查找，缓存把磁盘读变成内存读。
3. **缓存三大问题 + 分布式锁**：缓存击穿的互斥锁方案，在单机用 JVM 锁即可，跨节点就要升级成分布式锁。
4. **自动装配 + 缓存**：Redis 的自动配置就是"引入依赖即生效"的典型例子，`@ConditionalOnClass` 判断 Redis 客户端是否存在。
